## Work item 1 — Super-Admin org creation seeds per-app RBAC

### Why

When the QuikIT Super Admin created a new org via
`POST /api/super/orgs` (or toggled an app on via
`POST /api/super/org-app-access/:orgId`), only the `quikit.OrgAppAccess`
row was inserted. The granted apps' own RBAC tables
(`AppRole` / `RolePermission` / `UserAppRole` in `app_quikscale`,
`app_quiktrack`) stayed empty until a user lazily triggered the seeder on
first login. The freshly-invited Org Admin therefore had no role inside
any app and saw "No roles available" everywhere.

The required behaviour: when access is granted, eagerly seed the same
shape the QuikScale invite flow already creates — `AppRole(admin)` +
all `RolePermission` rows + a `UserAppRole` row binding the Org Admin to
the admin role — inside every granted app's schema. Defensive no-op for
apps that don't expose `/api/internal/provision-roles` yet (`quikvc`,
`quikconstruction`, `quiksocial` — they don't have AppRole tables today,
which was confirmed by inspecting `packages/database/prisma/schema.prisma`).

### Code changes

| File | Change |
|---|---|
| [apps/quikscale/app/api/internal/provision-roles/route.ts](apps/quikscale/app/api/internal/provision-roles/route.ts) | Now accepts optional `adminUserIds: string[]`. After seeding the default roles, calls `ensureUserOnRole` for each user id so a `app_quikscale.UserAppRole` row is created linking them to the admin AppRole. |
| [apps/quiktrack/app/api/internal/provision-roles/route.ts](apps/quiktrack/app/api/internal/provision-roles/route.ts) | **NEW**. Mirror of the QuikScale endpoint. Calls QuikTrack's `seedAllDefaultRoles` + `ensureUserOnRole` so the same admin AppRole + RolePermission + UserAppRole rows land in `app_quiktrack` (`QtAppRole` / `QtRolePermission` / `QtUserAppRole`). |
| [apps/quikit/lib/provisionAppRoles.ts](apps/quikit/lib/provisionAppRoles.ts) | **NEW** helper. `provisionAppRoles(app, orgId, adminUserIds)` fires a single fire-and-forget `/api/internal/provision-roles` call. `provisionAppRolesForOrg(apps, orgId, adminUserIds)` fans out in parallel with `Promise.allSettled`. Uses per-slug env override (`QUIKSCALE_URL`, `QUIKTRACK_URL`) falling back to `App.baseUrl`. |
| [apps/quikit/app/api/super/orgs/route.ts](apps/quikit/app/api/super/orgs/route.ts) | After the create-org transaction, calls `provisionAppRolesForOrg` for every app in `appsToProvision`, passing the just-invited admin's user id so the admin's `UserAppRole` row is wired the moment they accept the invite. `appsToProvision` query now selects `slug` and `baseUrl`. |
| [apps/quikit/app/api/super/org-app-access/[orgId]/route.ts](apps/quikit/app/api/super/org-app-access/%5BorgId%5D/route.ts) | Removed the QuikScale-only hand-rolled `fetch` block. Now looks up every `OrgMember` with `role=org_admin` for the tenant and passes their user ids through the shared helper, so subsequent app grants also seed admin assignments — for any app, not just QuikScale. |

### Database changes

**None.** The existing models in
`packages/database/prisma/schema.prisma` were used as-is:

- `app_quikscale.AppRole` / `RolePermission` / `UserAppRole`
- `app_quiktrack.AppRole` / `RolePermission` / `UserAppRole`
  (Prisma names `QtAppRole` / `QtRolePermission` / `QtUserAppRole`,
  mapped via `@@map`)

No migrations were generated.

## Work item 2 — Invitation email link redirects to the launcher (`:3001`)

### Why

Onboarding emails rendered the "Set Up My Account" link as
`http://localhost:3000/invitations/accept?token=…` because the email
renderer in three apps was reading `NEXT_PUBLIC_AUTH_URL` /
`NEXTAUTH_URL`. Those env vars point at the central auth host (`:3000`)
or the calling app's own host (`:3002`/`:3003`), not at the QuikIT
launcher (`:3001`). The user wants every invitation link to land on the
launcher.

### Code changes (email renderer base URL)

The base URL now sources from `QUIKIT_URL` / `NEXT_PUBLIC_QUIKIT_URL`
(both existing env vars — no new variable introduced) with
`http://localhost:3001` as the dev default.

| File | Change |
|---|---|
| [apps/quikit/lib/email.ts](apps/quikit/lib/email.ts) | `sendOnboardingInvitationEmail` now reads `QUIKIT_URL` / `NEXT_PUBLIC_QUIKIT_URL` instead of `NEXT_PUBLIC_AUTH_URL` / `NEXTAUTH_URL`. Dev fallback `http://localhost:3001`. |
| [apps/admin/lib/email.ts](apps/admin/lib/email.ts) | Same swap. The chain was `NEXT_PUBLIC_AUTH_URL ?? APP_URL ?? NEXTAUTH_URL ?? "http://localhost:3000"` — now `NEXT_PUBLIC_QUIKIT_URL ?? QUIKIT_URL ?? "http://localhost:3001"`. |
| [apps/quikscale/app/api/org/users/route.ts](apps/quikscale/app/api/org/users/route.ts) | Same swap on the inline `appBaseUrl` computation inside the invite-from-inside-QuikScale flow. |

### Environment-variable / docs changes

The runtime `.env.local` files in all five apps **already had
`QUIKIT_URL=http://localhost:3001`** set — verified by grepping each
app's `.env.local` (auth, quikit, admin, quikscale, quiktrack). No
changes needed to live env files for this work item. Only the example
docs were updated:

| File | Change |
|---|---|
| [apps/admin/.env.local.example](apps/admin/.env.local.example) | Added `NEXT_PUBLIC_QUIKIT_URL=http://localhost:3001` and `QUIKIT_URL=http://localhost:3001` with a comment explaining they drive the invitation-email landing host. |
| [apps/quikit/.env.local.example](apps/quikit/.env.local.example) | Fixed the commented-out `QUIKIT_URL` from `:3000` (wrong — that's the auth host) to `:3001` (the launcher's actual dev port). |

### Database changes

**None.**

## Work item 3 — Launcher serves `/invitations/accept` (Set-Password screen)

### Why

The email link now points at `:3001/invitations/accept`, but the
launcher had no such route — the auth app at `:3000` was the only host
that served the Set-Password page. We needed the launcher to natively
serve the page so the user never bounces to `:3000`.

After two iterations, the final shape was: render the same marketing
landing as the launcher home page (image of trees + QuikIT branding),
and let the existing `LoginModal` (which is auto-mounted by the
marketing layout) auto-open in a new **"invitation"** view that mirrors
the Set-Password form from the auth app's dark `SignInComponent`, but
styled to match the marketing modal's light "paper" theme.

## Work item 4 — Google / Microsoft SSO buttons on the marketing modal

### Why

The marketing `LoginModal`'s **Continue with Google** /
**Continue with Microsoft** buttons silently no-op'd. Root cause
identified by reading `packages/auth/index.ts` lines 164 & 197:
`createAuthOptions` registers each OAuth provider only when both env
vars are present:

```ts
...(process.env.GOOGLE_CLIENT_ID && process.env.GOOGLE_CLIENT_SECRET
  ? [GoogleProvider({ ... })]
  : [])
```

`apps/auth/.env.local` had the credentials; `apps/quikit/.env.local`
did not. NextAuth on `:3001` therefore had no Google or AzureAD
provider registered at all, and any signin attempt resolved to a no-op.

The button's client-side implementation (hand-rolled CSRF-form POST to
`/api/auth/signin/{provider}`) was fine — only the server-side provider
registration was missing.

### Code changes

| File | Change |
|---|---|
| [apps/quikit/app/(marketing)/_components/login-modal.tsx](apps/quikit/app/(marketing)/_components/login-modal.tsx) | One short-lived alternate implementation (`next-auth/react`'s `signIn()`) was tried and reverted in the same session per user request. The committed state is the original hand-rolled CSRF-form POST — unchanged from before today. |

### Environment-variable changes (live `.env.local`, manual)

| File | Change |
|---|---|
| [apps/quikit/.env.local](apps/quikit/.env.local) | **Appended** the OAuth credential block, mirroring `apps/auth/.env.local`: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `MICROSOFT_TENANT_ID`. After restarting the launcher's dev server, `createAuthOptions` registers both providers and the SSO buttons follow the same NextAuth signin chain as `:3000`'s `/login` page. |

### Database changes

**None.**

### Out-of-tree action required (provider consoles, not code)

For SSO to complete the round-trip, the OAuth app registrations for the
above `CLIENT_ID`s need `http://localhost:3001/api/auth/callback/...`
added as authorized redirect URIs:

- Google Cloud Console → OAuth client → Authorized redirect URIs →
  `http://localhost:3001/api/auth/callback/google`
- Microsoft Entra ID → App registration → Authentication → Web →
  `http://localhost:3001/api/auth/callback/azure-ad`

If those aren't already on the allow-list (alongside the existing
`:3000` entries used by the auth host), the provider returns
`redirect_uri_mismatch` after the consent screen.
