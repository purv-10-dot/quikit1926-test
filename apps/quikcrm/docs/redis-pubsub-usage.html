Redis Pub/Sub in QuikCRM — Where It's Used and Why It's Needed

A short reference explaining how Redis Publish/Subscribe powers real-time features in QuikCRM, which parts of the code use it, and whether it is actually necessary.

App: apps/quikcrm Feature area: Real-time updates (SSE) Prepared for: Engineering / Management review
✓

Yes — Redis Pub/Sub is genuinely needed, and it is implemented correctly.

It powers instant, no-refresh updates for notifications and the leads board. The implementation follows Redis best practices (dedicated subscriber connections, tenant-isolated channels, graceful fallback). The only gap is missing automated tests for the two streaming routes.

1. What is Pub/Sub used for?

Redis Pub/Sub is a lightweight messaging channel: one part of the system publishes a message and any part currently subscribed receives it instantly. QuikCRM uses it as a real-time "nudge" — the moment something changes on the server, connected browsers are told to refresh, without the user pressing anything.

It is used in exactly two features:

  • Notifications — the bell icon updates the instant a new notification is created.
  • Leads board (Kanban) — when a lead is created, updated, moved, or deleted, everyone viewing the board in that organization sees the change live.

2. How it works — end to end

The important point for review: the notification's actual data lives in the database (Postgres). Redis only carries the instant "something changed" signal. Nothing is lost if Redis is unavailable.

4. Is Redis necessary here?

Yes — for the real-time experience. Without Pub/Sub, users would only see new notifications and lead changes after manually refreshing or waiting for a slow poll. But the design is deliberately resilient: Redis is treated as an optional enhancement, not a hard dependency.

FeatureUses Pub/Sub?If Redis is down…
Notifications (bell)YesStill works — falls back to refreshing every 60 seconds instead of instantly.
Leads board live viewYesStill works — updates on next refresh instead of instantly.
All notification dataNoUnaffected — stored in and read from the database.
Rest of the CRM (leads CRUD, contacts, accounts, auth)NoFully unaffected.

5. Is it implemented correctly?

The core implementation follows Redis and SSE best practices:

  • Dedicated subscriber connection — uses .duplicate() because a Redis connection in subscribe mode cannot run other commands. This is the correct, required pattern.
  • Tenant & user isolation — channel names include the organization (and user) ID, so no data can leak between customers.
  • Graceful degradation — if Redis is missing or unreachable, the app returns a clean status and the browser falls back to polling.
  • Connection hygiene — 25-second heartbeats keep the stream alive through proxies; connections are cleaned up when the user leaves the page.
  • Correct data model — Pub/Sub is used only as a live signal; the database remains the source of truth, so no messages are ever "lost."
One gap to note (for transparency) The two streaming routes (/api/notifications/stream and /api/leads/stream) do not yet have automated tests, which the project's contribution rules require for every API route (unauthenticated → 401, tenant isolation, happy path). This is a follow-up task, not a functional bug — the feature works as intended today.
One-line summary for the manager QuikCRM uses Redis Pub/Sub to deliver instant notification and lead-board updates to the browser. It is correctly implemented, isolated per customer, and safe to run without Redis (it simply falls back to periodic refresh). The database — not Redis — holds the actual data. Recommended follow-up: add automated tests for the two streaming routes.
