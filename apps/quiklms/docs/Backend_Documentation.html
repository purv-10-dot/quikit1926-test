1. System Overview & Tech Stack

QuikSkill LMS is a multi-tenant Learning Management System serving two tenant archetypes from a single codebase: Corporate (employee training, compliance, manager hierarchy) and School (batches, attendance, credits, payouts, parents, live classes, proctored exams). The backend is a modular NestJS monolith exposing a REST API plus two Socket.IO gateways.

2. Architecture & Multi-Tenancy Model

Every business record carries a tenantId. A request's tenant is resolved from the JWT payload, the subdomain (e.g. company1.localhost), or an X-Tenant-Key header (TenantResolverMiddleware). TenantGuard blocks cross-tenant reads/writes; SUPER_ADMIN bypasses tenant scoping to administer all organizations.

  • Tenant types: corporate | school — drives which feature flags & modules are active (stored on Tenant.tenantType + Tenant.featureConfig).
  • Feature flags: per-tenant featureConfig object toggles courses, SCORM, compliance, manager reports, batches, attendance, homework, credits, payouts, video classes, parent portal, messaging, certificates, analytics, approval workflow.
  • Content sharing: SUPER_ADMIN authors master courses / certificate templates in a global library and pushes copies to selected tenants (shared-content, selectedTenants).
  • Approval workflow: SUB_ADMIN / tenant-created courses & certificates can require TENANT_ADMIN or SUPER_ADMIN approval (approvalStatus fields).

4.5 File Storage (AWS S3)

  • Presigned PUT (UploadService): browser uploads directly to S3. Key format tenants/{tenantId}/uploads/{uuid}-{fileName}; returns uploadUrl, fileKey, fileUrl.
  • Presigned GET (S3PresignedService): time-limited read URLs (default 3600s); handles full URLs, bare keys, data URLs.
  • TUS resumable uploads (@tus/server) for large media at POST /upload/tus.
  • SCORM: zip parse/extract/validate (manifest.xml) up to 500 MB.
  • Storage quotas: per-tenant storageLimit (GB); usage tracked & surfaced via /tenants/usage, /audit/storage/*.

6. Complete Data Model — All Collections / Future Postgres Tables

Every collection below maps to a PostgreSQL table. Mongo ObjectId → uuid or bigint PK; ObjectId ref→X → foreign key; embedded [subdoc] arrays → either a child table (1-to-many) or a jsonb column; Map/Object → jsonb; enums → Postgres enum or text+CHECK. All business tables include tenantId (FK to tenants) and Mongoose timestamps give createdAt/updatedAt.

55 collections total. Sub-documents (arrays of objects) are flagged inline — these are the main normalization decisions for the relational schema.

8. MongoDB → PostgreSQL Migration Guidance

8.1 Type & Relationship Mapping

MongoDB / MongoosePostgreSQLGuidance
_id: ObjectIduuid (or bigserial)Use uuid + a lookup map during ETL to preserve references; or keep the 24-char hex as char(24) short-term
ObjectId ref→Xuuid FK + REFERENCESAdd FK constraints & indexes; enforce ON DELETE rules previously implicit
Embedded array of subdocsChild table (1:N) or jsonbNormalize high-query arrays (batch.schedule, payout.adjustments, message.reactions, exam.questions, levelHistory, callAttempts). Keep low-value config blobs as jsonb
Object config blobs (featureConfig, settings, providerMetadata, lessonProgress, answers Map)jsonbKeep as jsonb; add GIN indexes where filtered
enum string fieldsPostgres ENUM or text + CHECKAll enum value lists are documented in §6 — reproduce exactly
Mongoose timestampscreated_at / updated_at timestamptzDefault now(); trigger for updated_at
TTL index (otps, analytics-cache)Scheduled cleanup job / partial indexPostgres has no TTL — use a cron DELETE WHERE expires_at < now()
Unique compound (tenantId,…)UNIQUE constraintSparse-unique → partial unique index WHERE col IS NOT NULL

8.2 Recommended Table Groups & Normalization Decisions

  • Join tables to create from arrays: group_members, batch_students, batch_substitute_teachers, course_modules (order), conversation_participants, course_selected_tenants, certificate_selected_tenants, user_parents/children, exam_questions, payout_completed_classes.
  • Child tables for queried subdocs: lessons (from module.lessons), payout_adjustments, message_reactions, call_attempts (escalation + student-reminder), teacher_level_history, batch_schedule, academic_terms, academic_holidays, homework_rubric_scores.
  • Keep as jsonb: tenant *Config blobs, exam/assessment settings, progress.lessonProgress, exam-session.answers, proctoringFlags, providerMetadata, notificationPreferences, analytics event/cache data.

8.3 Migration Sequence (suggested)

  1. Stand up Postgres schema with an ORM (Prisma recommended for Next.js) reproducing §6 exactly, including enums & FKs.
  2. Build an ETL that walks each Mongo collection, generates a UUID per _id, stores an old→new id map, then re-points all refs.
  3. Migrate in dependency order: tenants → users → courses/modules/lessons/assessments → progress/assignments/certificates → school-ops → exams/proctoring → logs/analytics.
  4. Replace Mongoose models with ORM models module-by-module; the REST contract (§7) stays identical so the frontend is unaffected.
  5. Swap TTL indexes for cron cleanups; re-create unique & performance indexes noted in §6.
  6. Keep Redis/Bull, S3, Socket.IO, Twilio, OpenAI, OAuth unchanged — none depend on the database engine.
Key insight: Because every endpoint is already tenant-scoped and DTO-validated, the API surface (§7) is engine-agnostic. The migration is almost entirely at the persistence layer — controllers, guards, queues, gateways and integrations port across unchanged.
